## 1. Source evidence and decision requested

- `crates/talos-tools/src/search_backend/transport.rs`: PreparedTransportRequest owns invocation ID and bytes, caps request payload at 16 KiB; SearchTransport validates exact endpoint and authority before DNS and again immediately before logical send. It pins resolved addresses, freezes proxy selection, disables redirects/retry by client policy, uses identity encoding, and reserves cumulative bytes before extending its body buffer. Existing response exposes only status/body, has no early Content-Length or per-response limit, and has no typed MCP content-type/version/session fields. Do not replace or duplicate its authority machinery.
- `crates/talos-mcp/src/client/transport.rs`: generic Streamable HTTP creates its own reqwest client; reads response.text() before status handling; SSE selects first matching ID and may ignore malformed events; error strings can include remote body or RPC data. Dispatcher permits unknown-method initialization fallback; facade accepts defaulted name/schema and arbitrary text results. These are existing compatibility semantics, not acceptable protected search admission.
- `crates/talos-mcp/src/client/transport/offline_search_tests.rs`: I337 local synthetic four-POST lifecycle, two fixed names, exact query-only input schema and structuredContent.results with URL/title. Its 2024-11-05 handshake + POST fixture is not evidence of real Streamable HTTP compatibility or actual vendor schemas.
- Manifest inspection: talos-mcp normal workspace edges = agent/core/plugin/permission; agent normal = core/permission/sandbox/skill/plugin/memory/session; plugin normal = core/permission/text; permission/sandbox/session -> core; core/skill/memory/text have no named talos workspace dependency in inspected manifests. Both agent and mcp refer to tools only as dev-dependencies. No normal dependency path from mcp to tools found by reading these manifests, but this is not executed Cargo metadata or proof of all target/feature combinations. Tools normal edges include core/text and optional conversation/permission/sandbox, with conversation -> core/plugin. Current standalone network feature has no direct dependency on mcp/agent.

Options:

A. tools -> mcp: reuse protocol in its existing owner but pull Agent/plugin/session dependencies into built-in network feature; test dev-dependency cycles and feature isolation would need proof. Not recommended.

B. New talos-mcp-wire published crate or refactor existing mcp into independent wire-only feature: clean ownership but changes release/dependency design beyond this bounded slice. Not recommended without separate decision.

C. **Recommended proposal**: a minimal network-free JSON-RPC/SSE framing module in existing talos-core (already depended on by tools and mcp), with shared encode/decode/framing primitives only. Keep SearchTransport and all search-specific admission, result projection and invocation orchestration private to talos-tools. Retain generic transport, dispatcher and facade behavior. No new crate, external dependency, production dependency edge or additional Cargo feature required by this proposal. This is a deliberate proposed additive cross-crate API and ownership change, not already accepted by ADR-085. Even a doc-hidden public module is public. Review the exact minimal interface and compatibility contract and explicitly accept a narrow ADR-085/090 decision/amendment before implementing it; if rejected, return for review of a different seam. No automatic extraction or code authorization merely because this proposal is published.

## 2. Proposed ownership and minimal interface

- Shared wire module: pure, no reqwest/tokio I/O, permission, URLs, endpoints, session registry, provider/profile or routing concerns. Reuse existing request/notification envelope serialization and SSE event framing; expose only the narrow encoding and bounded event/message decoding required by both clients. Preserve existing generic RpcResponse/RpcErrorBody exports and serialized shapes; do not move public nominal types or change their fields. Use existing serde/serde_json. Keep generic compatibility policy (including old parser behavior) separate from strict policy; characterize old LF/CRLF/multiline and malformed input first. A shared lexer/framer with explicitly selected compatibility vs strict validation is preferable to two independent protocol engines. No new public AgentTool or runtime entry point. Exact signatures are reviewed before code.
- Private search module: `talos-tools/src/search_backend/hosted_mcp.rs` (proposed), closed profile enum (Exa/Parallel synthetic profiles), immutable prepared search invocation, typed bounded results/errors, finite lifecycle, no generic tool execution API. The protocol cannot choose or derive URL, HTTP method, credential, proxy or tool name from remote data. Prepared object owns query and fixed profile before approval; consumes itself once with the same manifest and injected ToolNetworkAuthority. Actual endpoint must be configured by trusted construction; only explicit local fixture endpoints exist in this slice. No public URL constants enabling a vendor path.
- Narrow MCP-specific extension inside existing SearchTransport: use the same logical-send and DNS/proxy fence. Fixed POST, fixed Accept (JSON/SSE), fixed JSON body, optional validated protocol version header, identity encoding; no arbitrary header map or credential injection. Return only bounded typed content-type, status and body; reject session-bearing response for initial stateless-only subset (below). Keep normal compatibility requests and response behavior unchanged. No new redirect, retry, implicit proxy or network authority mechanism.
- Require complete graph proof with pinned `cargo metadata --locked --format-version 1` including isolated features and workspace; compare Cargo.lock and normal dependency closure. No changes to unrelated core types, permission policy, runtime composition, MCP-002/#1033 or NET-001/#199. If any new API/feature/graph change exceeds this design, stop for review.

## 3. Deliberately restricted handshake profile

The original I337 fixture uses protocolVersion 2024-11-05, which predates standardized Streamable HTTP. See versioned [MCP 2025-06-18 transport](https://modelcontextprotocol.io/specification/2025-06-18/basic/transports) and [lifecycle](https://modelcontextprotocol.io/specification/2025-06-18/basic/lifecycle). This proposal pins the initial **stateless handshake subset** to 2025-06-18 for local protocol-oriented fixtures, and reuses 2024-11-05 I337 fixture shapes only as historical test evidence (do not modify or relabel I337). Not a claim of complete MCP conformance or current vendor support. A provider that requires another revision, stateful sessions, pagination, server-driven interaction or the newer lifecycle is unsupported; no silent downgrade, discovery, retry or fallback. Such expansion requires distinct design/admission evidence. Actual wire fixtures and rights remain separate #848 gates.

One invocation: initialize (ID 1; empty client capabilities) -> notifications/initialized (no ID; HTTP 202 and empty body) -> tools/list (ID 2; no pagination) -> tools/call (ID 3, exactly one pinned tool). Initialize must return supported exact version, valid serverInfo and tools capability. Subsequent POSTs carry fixed negotiated MCP-Protocol-Version. Reject Mcp-Session-Id (stateful session unsupported), auth challenges, unnegotiated capability or unexpected server requests/notifications, and any invalid response before further sends. No GET/DELETE, server cancellation notification, resumption, reinitialization or extra request; local cancellation drops the future/connection and stops future sends, does not claim remote execution stopped. Statefulness and remote teardown are release residuals, not hidden side effects permitted on live vendors.

Strict JSON-RPC 2.0 single object, exactly one integral expected ID (not bool/string/null), exactly one result/error, reject duplicate keys and mismatched/duplicate IDs. No unknown-method initialize success. Strict JSON or SSE by bounded content-type parsing (not substring match); accept bounded finite SSE framing including fragmentation, LF/CRLF and multiline data, require one matching response and reject extra responses before stream end. If stream never ends, deadline terminates; do not return early and miss duplicates. Reject unknown interactive messages, malformed/truncated event, unsupported encoding/charset, batch, excess depth/events. No raw messages in logs or outputs.

Pin I337's synthetic profiles web_search_exa and web_search with exact query-only inputSchema (object, query string required, no additional properties). Do not trust readOnlyHint, description, arbitrary schema instructions or discovered tool names. Initial conservative admission requires exactly one selected descriptor and no duplicate/missing/drifted names; other advertised tools convey no authority. Reject extra descriptors in the initial profile (preserve I337 conservative negative fixtures); do not send calls to research/fetch/paid/discovered tools even if present. No schema inference or provider fallback. Results must be typed structuredContent.results; project only URL/title/optional bounded snippet, reject errors, missing shape, oversized/invalid rows, non-HTTP(S) URL, userinfo/control characters. No remote content as tool definition, no resource/image execution, no fetch. Result URLs are data, not authority. Both profiles remain synthetic pending vendor wire qualification.

## 4. Proposed numeric limits (review targets, not observed capacity)

| Item | Bound |
|---|---|
| Invocation deadline | 30 s absolute monotonic; includes DNS, send, read, parse and projection; no reset |
| Logical POSTs | 4; existing transport budget at most 8 accounting units (one CONNECT + one application send per proxied POST) |
| Query | 1–4096 UTF-8 bytes, nonblank; result limit 1–20 |
| Serialized outgoing payload | 16 KiB per POST, 64 KiB cumulative; bounded writer before grow/send |
| Response body | 64 KiB per response, 256 KiB cumulative, including non-success bodies if read |
| Decoded bytes | identity only, same limits; reject compressed/unknown encoding before read; no decompressor or expansion path |
| Response headers | existing 64 headers / 16 KiB combined upper bound; validate only fixed typed metadata |
| SSE | <=32 events total, <=16 KiB per event data; line/data accumulation charged before append; no resumability |
| JSON | max depth 32, <=8192 value/key tokens per invocation; bounded visitor or pre-scan before allocating nested values, reject duplicate keys |
| Results | <=20 rows; URL <=2048 bytes, title <=512 bytes, optional snippet <=2048 bytes; <=32 KiB projected output |

Use checked arithmetic and single invocation counters, not a fresh budget per step. Reject known oversized Content-Length before body accumulation; count actual chunks before extend, including absent/false length and non-success; do not claim control of allocations inside reqwest/hyper's own finite parser/buffers. Fresh clients avoid reuse after invalid framing. Do not drain unbounded error bodies; status-only terminal outcome may drop body immediately without exposing it. For malformed short/long framing, fail closed rather than relying on Content-Length. Test exact/one-over boundaries and cumulative exhaustion on each step. Cancellation/deadline observed before every logical send, during body read and before projection; no background task or detached request survives local cancellation.

## 5. Authority and connection-level evidence

Preserve ADR-090 actual logical start fence and existing proxy semantics. Deny before DNS, recheck after resolution and immediately before actual request start; same immutable endpoint/method/path/manifest/configuration and frozen proxy through all steps. Explicit no redirect/retry; future send after revocation denied; previously-started CONNECT/TLS/request cannot be unsent. Direct resolution pins only policy-permitted addresses and rejects mixed/disallowed/wrong-port/empty/too-many answers. For existing trusted proxy snapshot, the pinned physical peer is the approved proxy, which owns remote hostname resolution; do **not** claim observation of the ultimate target IP behind a proxy. Validate actual proxy peer and CONNECT target; if a future profile requires direct target-IP proof and cannot supply it through approved proxy semantics, fail closed, never silently bypass proxy. Test local TLS fixtures, injected DNS and local proxy, both selected/bypassed routes, snapshot mutations, deny/revoke between DNS and send, mixed answer, wrong port, resolution drift, denied sink receives zero connections, no credentials or arbitrary header forwarding. Private/loopback exceptions only explicit test manifest, never a new production exception. Observe actual accepted connection peer/CONNECT target and method counts; avoid external traffic.

Terminal outcomes are fixed codes/enums: invalid query/limits; unauthorized/stale; address/DNS; connection-refused/network/transport (separate TLS/proxy only when typed evidence, otherwise generic safe transport failure); redirect; auth 401/403; rate 429; HTTP other including 5xx; request/body/decode/event/depth budgets; protocol/version/ID/schema/tool/result invalid; RPC/tool error (no upstream text); no results; deadline/cancellation. No raw reqwest or serde error text, query, URL with parameters, response, proxy credentials, headers, session or tokens. Access/rate/challenge/HTTP error never causes retry/fallback or billing. Only redacted bounded test receipts.
