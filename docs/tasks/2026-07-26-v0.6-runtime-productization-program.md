# Talos v0.6 Runtime Productization Program

> Document status: In Progress

> Current active iteration: none
> Implementation authority: none; I167/TUI-040 is Complete and I158 remains blocked by ADR-053

## 1. Purpose

This program turns the accepted ADR-052 direction into a bounded development sequence that a
frontline developer can execute without inventing architecture or expanding scope.

The program has five outcomes:

1. close the current user-visible TUI resize/narrow-width defect;
2. close the provider configuration lifecycle gap;
3. consolidate built-in tool registration without changing behavior;
4. implement the ADR-052 SDK composition, feature, and sandbox-policy boundaries;
5. produce a version-aligned v0.6 SDK and publication-readiness evidence packet.

This plan coordinates work. It is NOT the source of truth for individual Story acceptance. Each
implementation iteration selects exactly one Ready Story, and the Story remains the scope and
acceptance owner.

## 2. Governing Decisions

- ADR-024: `talos-runtime` is the embeddable runtime facade.
- ADR-052: SDK publication and composition boundary.
- ADR-053: tool registration composition. This ADR is created as Proposed by this program and MUST
  be accepted before ARCH-034-R01 or I158 becomes Ready.
- Existing permission, sandbox, provider, session, TUI, and release ADRs referenced by child Stories.

## 3. Program Outcome

At program close:

- TUI resize and extremely narrow rendering are robust.
- A user can remove a provider config or clear its credential without hand-editing TOML.
- Built-in tool registration has one explicit contribution/composition model with preserved
  print/TUI/MCP behavior.
- `talos-tools` has real Cargo feature gates with a lightweight local read-only default.
- CLI and SDK share one internal composition implementation while retaining separate public entrypoints.
- `talos-runtime` exposes an explicit `SandboxFallbackPolicy` and `RuntimePreset::coding()`.
- An external SDK fixture proves the supported embedding path.
- A complete dry-run/readiness packet exists for a future v0.6 crate publication decision.
- No real crates.io publish, tag, or release occurs without a separate maintainer authorization.

## 4. Non-Goals

This program does NOT authorize:

- Desktop or GPUI implementation;
- v1.0 release;
- multi-agent architecture;
- a new composition crate;
- a general-purpose third-party UI SDK;
- independent per-crate versioning;
- real `cargo publish`;
- a Git tag, GitHub Release, or product release;
- changing permission defaults merely to make tests pass;
- changing sandbox policy inside `talos-sandbox`;
- wiring `talos-models` into CLI, TUI, agent, or runtime.

## 7. Activation Contract

Before activating any iteration, complete the full inventory per the formal SOP
(`docs/sop/START-ITERATION.md`, `docs/sop/ITERATION-WORKFLOW.md`,
`docs/sop/CHANGE-CONTROL.md`):

1. read `docs/sop/START-ITERATION.md`, `docs/sop/ITERATION-WORKFLOW.md`, and
   `docs/sop/CHANGE-CONTROL.md`;
2. inventory every Active, Review, Planned, and Blocked iteration;
3. confirm no other implementation iteration is `Active`;
4. confirm every Review iteration has an explicit disposition: complete, remain in Review,
   pause, or a recorded blocking decision;
5. confirm every prior Planned iteration has an explicit disposition: activate, defer, remain
   Planned with reason, remain Blocked, or supersede;
6. confirm the Selected Story is `Ready`;
7. confirm every dependency and human gate is satisfied;
8. append an Activation Record to the iteration owner doc FIRST;
9. then change the iteration to `Active`;
10. then change the Selected Story to `In Progress`;
11. finally synchronize `docs/BOARD.md` and the index docs.

When an iteration becomes `Active`, its selected `Ready` Story becomes `In Progress`.

A Board row is not an Activation Record. A Planned iteration is not implementation authority.

If a dependency is not satisfied, keep the iteration Planned/Blocked. Do not implement around the gate.

## 8. Common Frontline Rules

Every implementation iteration follows these rules:

- implement only the selected Story;
- use existing patterns before adding abstractions;
- write focused failing tests before changing behavior where practical;
- do not add crates or dependencies unless the Story explicitly authorizes them;
- do not change public APIs unless an accepted ADR and the Story authorize the exact change;
- one logical Story per implementation commit;
- do not push, tag, publish, or create a release without fresh maintainer authorization;
- behavior-facing work requires actual binary/TUI evidence, not unit tests alone;
- if three approaches fail, stop and record the blocker instead of continuing speculative changes.

## 9. Program-Level Validation

Every implementation iteration runs its focused tests plus:

```bash
cargo fmt --all -- --check
cargo check --workspace --locked
cargo clippy --workspace --locked -- -D warnings
cargo test --workspace --locked
scripts/validate_project_governance.sh .
git diff --check
```

Security- or publication-sensitive iterations add the specific checks listed in their Story.
