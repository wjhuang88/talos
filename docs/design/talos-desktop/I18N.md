# Talos Desktop Internationalization Baseline

> Status: design/product requirement for `DESKTOP-001`; no implementation authorization
>
> Initial supported UI locales: Simplified Chinese (`zh-CN`) and English (`en-US`)
>
> Related visual baseline: `docs/design/talos-desktop/DESIGN.md`
>
> Related product baseline: `docs/proposals/talos-desktop-goal-oriented-workspace.md`

## 1. Purpose

Internationalization is a first-class Desktop requirement, not a post-launch string-replacement task.
The first Talos Desktop implementation must be designed so the complete user-facing product can run
in either Simplified Chinese or English without changing Mission semantics, runtime facts, evidence,
or artifact identity.

The initial release target is deliberately small:

- Simplified Chinese: `zh-CN`;
- English: `en-US`.

The architecture should allow additional locales later without redesigning screens or moving
business logic into translation files, but this requirement does not authorize speculative locale
support beyond the two initial languages.

## 2. Core Boundary: Locale Is Presentation State

The selected UI locale is a **client/display preference**.

Changing language must not mutate or invalidate:

- Mission identity;
- Work Graph identity or topology;
- Goal/WorkUnit revisions;
- Execution Baselines;
- Completion Claims;
- Evaluation subjects or exact-revision bindings;
- Validation/Evidence records;
- Artifact identity or file contents;
- Delivery revision identity.

In other words:

```text
canonical Mission / Work / Evidence state
                 |
                 v
        locale-aware projection
          /              \
       zh-CN            en-US
```

A locale switch changes presentation, not the canonical work fact being presented.

## 3. What Is Localized

The Desktop localization layer should own product-controlled user-facing text, including:

- navigation labels;
- page and section labels;
- buttons and menu actions;
- status labels;
- empty states;
- permission/approval UI text;
- plan-change and evaluation UI labels;
- application-generated activity labels;
- validation/evaluation presentation labels;
- settings labels and descriptions;
- error and recovery messages owned by Desktop;
- Delivery UI labels;
- accessibility names and tooltips;
- date/time/number presentation where locale-sensitive.

User-facing strings should be addressed through stable localization keys or an equivalent typed
message interface. New Desktop UI code should not scatter hard-coded English or Chinese strings
through view/layout code.

## 4. What Is Not Automatically Translated

The locale layer must not silently translate canonical or user-authored facts.

Keep the following in their source/original form unless a separate explicit product feature later
requests translation:

- user-authored Mission/Goal text;
- code and code comments;
- paths and filenames;
- commands;
- SHAs/revisions/IDs;
- raw stdout/stderr;
- provider/tool raw diagnostics;
- external document contents;
- external issue/PR titles;
- Artifact contents;
- validator raw evidence.

Machine facts can be surrounded by localized explanatory UI, but the fact itself remains unchanged.
For example:

```text
zh-CN: 12 个测试通过    cargo test
 en-US: 12 tests passed cargo test
```

The command and evidence identity are the same in both projections.

## 5. Agent-Generated Human Summaries

Talos may generate human-readable execution/activity summaries. These summaries should follow the
active Desktop display language where practical, but they remain **presentation summaries**, not
canonical evidence.

Requirements:

- selected locale may influence newly generated human summaries;
- raw events/evidence remain locale-independent;
- changing locale does not require regenerating historical evidence;
- if an existing generated summary is only available in another language, the product may show it
  as-is rather than fabricating a translated canonical fact;
- any future cached localized summary should be keyed by locale and source-event revision.

## 6. Locale Selection And Persistence

The initial Desktop should support:

1. **System default** — resolve the OS/application locale to the best supported Talos locale;
2. **Simplified Chinese** — explicit `zh-CN` selection;
3. **English** — explicit `en-US` selection.

Recommended negotiation behavior:

```text
zh / zh-CN / zh-SG -> zh-CN
en / en-*          -> en-US
other locale       -> en-US fallback
```

The exact regional mapping may be refined during implementation, but fallback must be deterministic
and safe.

The explicit user selection should persist as Desktop client configuration. It must not be stored as
a Mission property or session transcript fact.

A user should be able to change language from Settings without reinstalling or editing source files.
Prefer runtime switching if GPUI/app architecture can support it cleanly; if a restart is required in
the first implementation, the UI must state that clearly and the limitation must be recorded rather
than silently ignored.

## 7. Message Catalog And Formatting Requirements

The implementation should use a localization mechanism that supports more than direct key-to-string
replacement.

At minimum it must safely handle:

- named interpolation;
- plural/count-sensitive text;
- reordered placeholders between languages;
- locale-sensitive date/time formatting;
- locale-sensitive numbers where appropriate;
- fallback when a key is missing;
- development-time detection of missing/unused keys where practical.

Avoid constructing sentences by concatenating independently translated fragments such as:

```text
"Completed " + count + " goals"
```

The whole message should be localizable as one semantic unit.

Translation resources must not contain executable business rules, permission policy, Goal state
transitions, or evaluation authority logic.

## 8. Layout And Visual Design Requirements

Internationalization affects layout from the first mockup and GPUI spike.

### 8.1 No fixed-width assumptions for labels

Chinese and English differ substantially in word length, line breaking, and information density.
Controls must not rely on the exact width of one language.

Prefer:

- intrinsic sizing for buttons and labels;
- sensible min/max width constraints;
- wrapping for descriptive text;
- ellipsis only for genuinely secondary single-line content;
- adaptive spacing rather than manually tuned per-language coordinates.

Do not hard-code widths merely because the current reference screenshot happens to fit one string.

### 8.2 Preserve visual focus in both languages

The Execution page must preserve the same information hierarchy in both locales:

```text
Mission
  -> Current Goal
      -> Current Work
          -> Mission position
              -> Recent Activity
                  -> Change summary
```

English expansion must not turn the page into a dense dashboard or force additional permanent
panels. Chinese compactness must not be used as an excuse to fill empty space with more data.

### 8.3 Typography and CJK support

The sans-serif stack must render Chinese and Latin text cleanly on macOS, Windows, and Linux.
The implementation should prefer platform-native/system fallback behavior where it provides high
quality and avoids unnecessary bundled-font cost.

Requirements:

- correct CJK glyph coverage;
- stable baseline/alignment when Chinese and Latin appear in one row;
- line-height comfortable for Chinese body text;
- no assumption that monospace fonts provide acceptable Chinese UI glyphs;
- monospace remains reserved for code, paths, commands, IDs, and machine facts where appropriate.

### 8.4 Reference designs must be checked in both languages

The first GPUI visual spike should render the same core Execution page in both `zh-CN` and `en-US`,
not just replace a few labels in screenshots.

At minimum validate:

- Mission title/header;
- Current Goal;
- Current Work;
- compressed Mission path;
- Recent Activity;
- change summary shelf;
- navigation labels/tooltips;
- pause/stop/change-plan controls;
- settings language selector;
- one error/blocked state;
- one evaluation state.

## 9. Status And Domain Vocabulary

Status strings must be localized at the presentation boundary while their underlying enums remain
locale-neutral.

Example:

```text
Domain state          zh-CN             en-US
------------------------------------------------
Ready                 就绪              Ready
InProgress            进行中            In progress
Blocked               已阻塞            Blocked
NeedsInput            需要输入          Needs input
EvaluationPending     等待评估          Awaiting evaluation
Evaluating            评估中            Evaluating
Rework                返工中            Rework
Completed             已完成            Completed
Failed                失败              Failed
Inconclusive          无法判定          Inconclusive
```

The exact wording remains a UX/content decision and may be refined, but domain enum names must not
become display strings directly.

The same rule applies to terms such as Mission, Goal, Work Unit, Evaluation, Evidence, Artifact, and
Delivery. Product terminology should be reviewed for consistency in both languages before the first
public Desktop release.

## 10. Accessibility And Input

Internationalization must coexist with native input behavior.

The Desktop implementation must validate:

- Chinese IME composition in all editable text fields;
- composition/candidate windows without premature submit;
- copy/paste for mixed Chinese/English/code text;
- keyboard shortcuts that do not depend on localized visible labels;
- screen-reader/accessibility names in the active locale where supported;
- focus order independent of string length;
- text scaling without clipping localized labels.

IME correctness is a release-quality interaction requirement, not a cosmetic follow-up.

## 11. Search, Commands, And Shortcuts

Visible command names may be localized, but command identity and shortcut bindings must remain
stable and locale-neutral.

For a future command palette, prefer matching both:

- the localized display name;
- a stable command identifier/keyword set where useful.

Do not encode localized labels as persistence keys, command IDs, telemetry/event IDs, or protocol
values.

## 12. Error And Fallback Behavior

Internationalization failures must degrade safely.

Requirements:

- a missing translation key must not crash Desktop;
- fallback should resolve to the configured fallback locale, initially English;
- developer builds should make missing keys observable rather than silently hiding coverage gaps;
- malformed interpolation data should produce a safe fallback/error presentation, not undefined UI;
- unsupported OS locale must still launch a usable English Desktop.

## 13. Initial Implementation Acceptance

The first Desktop implementation slice that claims an internationalized UI must prove all of the
following:

- `zh-CN` and `en-US` catalogs exist and cover the selected Desktop slice;
- product-controlled visible strings in that slice are not hard-coded in view code;
- changing locale updates the selected UI language, with any restart limitation explicitly
  documented;
- the language preference is client-level persisted state;
- locale changes do not modify Mission/Goal/Evaluation revisions or canonical evidence;
- the Execution page remains visually coherent in both languages at normal laptop width;
- Chinese IME works in editable fields used by the slice;
- buttons, navigation, dialogs, empty states, errors, and accessibility labels in scope are covered;
- date/time/count formatting has deterministic locale-aware behavior;
- missing-key fallback is tested;
- raw artifacts, paths, code, commands, IDs, and evidence remain unmodified by localization.

## 14. Scope Boundary

This document does not:

- select a specific Rust i18n crate;
- authorize Desktop implementation;
- require every current CLI/TUI string to be internationalized;
- require translation of user-authored or external content;
- authorize more than `zh-CN` and `en-US` for the initial Desktop release;
- make locale part of Mission or Work Graph semantic identity.

The concrete library choice should be made at the GPUI implementation boundary using current Rust
and GPUI ecosystem evidence, while preserving the product and architecture requirements above.
